# IntelliCanvas — قائمة PRs مرحلة v0.9

**نقطة البداية:** `main` عند commit `d25e2e6` بعد دمج v0.8.3 Smart Crop.
**حالة PRs المفتوحة:** لا توجد.
**الهدف:** تنفيذ v0.9 تدريجياً من تثبيت الجودة إلى ميزات Intelligent Auto Enhance المقترحة، دون إضافة ميزات كبيرة قبل إثبات سلامة النظام الحالي.

## الحكم على التخطيطين

التخطيط السابق بعنوان **v0.9 — Polish & Testing** مناسب كخطة جودة وإطلاق، لأنه يعالج الاختبارات، عقود API، الأداء، الأمان، الوصول، والاستجابة. أما التخطيط المرفق بعنوان **v0.9.0 — Intelligent Auto Enhance** فهو مناسب كخطة ميزات منتج، لأنه يبني Auto Enhance وSmart Presets وBatch Processing وAdaptive Suggestions وQuality Gates.

لا ينبغي اختيار أحدهما وإلغاء الآخر. التخطيط الصحيح هو **تسلسل هجين**: PRs الجودة الحرجة أولاً، ثم Auto Enhance وPresets، ثم Batch وProfiles وQuality Gates، مع إبقاء الأداء والموثوقية كمسار مستمر. بهذا الترتيب لا نبني ميزات تعتمد على Pipeline وAnalysis قبل التأكد من استقرارهما.

- CI تمنع الدمج عند فشل أي فحص إلزامي.

## PR 8 — Intelligent Auto Enhance

**الفرع:** `feat/v09-auto-enhance`

### النطاق

إنشاء خطة تحسين كاملة قابلة للمراجعة بدلاً من عرض Suggestions منفصلة. يجب أن تكون الخدمة وصفية ولا تعدل الصورة مباشرة.

### الخدمة

أضف:

```
backend/app/services/auto_enhance_service.py
```

وتكون مسؤولة عن:

- استقبال Analysis Report.

- دمج Smart Suggestions المتوافقة.

- إزالة العمليات المتعارضة.

- ترتيب Pipeline.

- دمج Brightness أو Contrast المتكررين.

- حساب confidence النهائي.

- إنشاء explainability report.

- إرجاع Pipeline وصفية قابلة للتعديل.

### سياسة التعارض

| الحالة | القرار |
| --- | --- |
| Brightness مكرر | دمج إلى عملية واحدة |
| Denoise وSharpen | Denoise أولاً ثم Sharpen |
| Crop وResize | ترتيب حسب aspect ratio والهدف |
| Background removal وSmart Crop | Crop بعد إزالة الخلفية عند توفر mask |
| Confidence منخفض | عرضه للمراجعة وعدم إضافته تلقائياً |

### API المقترح

```
POST /api/auto-enhance/plan
POST /api/auto-enhance/preview
POST /api/auto-enhance/apply
```

Preview لا يغير الصورة أو History. Apply يستخدم Pipeline executor الحالي ويسجل History واحدة.

### معايير القبول

- الخطة قابلة للمراجعة والتعديل قبل Apply.

- Preview لا يغير History.

- Apply يسجل عملية واحدة مع provenance وanalysis hash وpipeline hash.

- المخرجات حتمية عند نفس المصدر والخيارات.

## PR 12 — Batch Processing

**الفرع:** `feat/v09-batch-processing`

### النطاق

تطبيق Preset أو Pipeline على مجموعة صور مع عزل النتائج واستقلال فشل كل صورة.

### نموذج الوظيفة

```
queued
→ running
→ completed
→ completed_with_errors
→ failed / cancelled
```

### المهام

- اختيار مجموعة الصور.

- Preview على صورة ممثلة.

- تطبيق Preset أو Pipeline.

- تنفيذ متسلسل أو بتوازٍ محدود.

- نتيجة مستقلة لكل صورة.

- عدم فقدان النتائج المكتملة عند فشل صورة أخرى.

- Retry للعناصر الفاشلة.

- إلغاء آمن.

- تقرير نهائي قابل للتصدير.

### قاعدة History

كل صورة ناجحة تحصل على History entry واحدة تحتوي على:

- batch job ID.

- preset ID.

- pipeline hash.

- عدد العمليات.

- parameters.

- analyzer report hash عند وجوده.

لا تنشئ Preview أو الصور الفاشلة History entries.

### معايير القبول

- partial failure ينتج `completed_with_errors` دون حذف النجاحات.

- Cancel لا يحذف النتائج المكتملة.

- lifecycle والنتائج مغطاة باختبارات Backend وBrowser.

# قواعد مشتركة لكل PR

1. ابدأ من آخر `main`، ولا تستخدم branch قديم.

1. أنشئ فرعاً واحداً لكل PR.

1. لا تخلط إعادة التصميم الشاملة مع تغيير API في PR واحد.

1. حافظ على API الحالي أو وثق أي breaking change بوضوح.

1. لا تجعل Preview يغير الصورة الحالية أو History.

1. كل Apply يجب أن يسجل العملية وفق القاعدة المناسبة.

1. استخدم Python للنتيجة المعتمدة، ولا تكتفِ بتغيير Canvas محلياً.

1. أضف اختبارات نجاح وفشل وحدود وأداء حسب نطاق PR.

1. شغّل الاختبارات من جذر المستودع.

1. حدّث `docs/current/system-status.md` عندما تتغير capabilities أو API أو dependencies.

1. اذكر في وصف PR طريقة التجربة اليدوية والقيود المعروفة.
